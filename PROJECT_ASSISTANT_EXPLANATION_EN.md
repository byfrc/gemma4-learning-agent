# My Project Assistant

I extended the existing Gemma4 learning platform by adding a new agent mode called **Project Assistant**. The base application already existed. My contribution is the new agent mode, its instructions and interface, and the features for discussing documents, source code, and images.

I followed the supplied *Adding a New AI Q&A Agent* guide and used `project_assistant` as the mode name. My goal was to let a user send their own material and receive an explanation of its actual contents, help with an error, or suggestions for improving their code.

The existing **AI Q&A** mode acts as a general course tutor and can retrieve relevant material from the subject's knowledge base. I designed **Project Assistant** around the user's attachments and selected documents. Both modes use the same local Gemma model; I gave the new agent different instructions and rules for choosing context.

1. **I registered the agent in the backend.** In `app/backend/app/schemas.py`, I added `project_assistant` to the shared `AgentMode` type used by chat requests, conversation creation, and conversation updates. Unknown mode names are still rejected. I made the agent available in both the AI and Java subjects while retaining the existing authentication, conversation ownership, and subject checks.

2. **I wrote a dedicated agent prompt.** In `app/backend/app/providers.py`, I added a Project Assistant entry to `AGENT_PROMPTS`. It asks the model to explain the main point first, explain code step by step when requested, distinguish facts from suggestions, and cite a filename only when that file supports the answer. For debugging, it should give a likely cause, a small proposed fix, and a way to check the result. I also separated this agent from the tutor's fixed assumptions about the hosting platform, so it can explain a user's Java program or other project without assuming that it uses the platform's own frontend, backend, or database.

3. **I added the interface and translations.** In `app/frontend/index.html` and `app/frontend/app.js`, I added the Project Assistant tab, heading, description, welcome text, and subject-specific placeholders. I provided English and Chinese text for these additions. The three example buttons are **Explain file**, **Debug an error**, and **Explain code**. Each button fills the message box so the user can edit the question before sending. I also made the box resize to keep the inserted text visible. Switching agent modes starts a separate conversation and preserves the previous discussion in history.

4. **I made attachments wait for Send.** I added a **Files** button, drag-and-drop support, and screenshot pasting. Selecting an attachment only adds it to the current conversation's draft. It does not immediately post a message or ask the model for a response. The user can remove an unsent attachment, add more files, and optionally write a question. Pressing **Send** submits the attachments and any text together. Sent files appear as cards in the chat, and images have previews. Drafts stay separate when switching conversations while the page remains open.

5. **I made written instructions optional.** A user can send just an image or just a file. A separate TXT file is not required. If the message box is empty, I generate an internal instruction asking the agent to analyze the new attachments: describe visible image content, summarize a document, or explain a code file's purpose, inputs, steps, and outputs. I exclude earlier chat material from this automatic analysis so the response focuses on what was just sent. If the user writes an instruction, I use that instruction instead. I save an attachment-only user message with empty text, so the interface does not display a question the user never wrote. A completely empty message, with neither text nor attachments, is rejected.

6. **I added combined request handling.** In `app/backend/app/main.py`, I added `POST /api/chat/attachments` for the files, chat settings, and optional question. `AttachmentChatRequest` accepts an omitted or empty written message. I validate the attachments, extract document text, prepare images, and pass the resulting material to the same generation function used by `/api/chat`. Messages without new attachments continue to use `/api/chat`. After successful generation, I save one user message containing the attachments and optional text, followed by one assistant message. If validation or generation fails, the frontend restores the draft for retrying. Generation failure does not add a chat message, and the upload handler rolls back its file changes when those files have not been replaced by a newer request.

7. **I added document and image processing.** I extended `document_parser.py` and `rag.py` to read source formats such as Java, Python, JavaScript, TypeScript, and JSON while preserving code indentation. Uploaded source code is read as text and is not executed. In `chat_images.py`, I validate PNG, JPEG, and WebP images, correct their orientation, prepare a model image bounded to 1,600 pixels per side, and create a small preview. I pass the actual image data to the model using Ollama's [vision input format](https://docs.ollama.com/capabilities/vision). Images are stored separately from the document retrieval index. Recent images can also be included in follow-up questions, with priority given to the current message.

8. **I controlled which documents become context.** I made retrieval use the documents selected for the conversation. Users can choose existing documents through **Choose uploaded files**, and newly sent documents join that conversation's selection. For short files, I include all indexed chunks when they fit within a 6,000-character evidence budget, even if the question has no matching keywords. Larger files receive bounded excerpts. Project Assistant does not automatically retrieve unrelated platform documentation when no documents are selected. For an attachment-only message, I use only the newly sent documents and images. For a question with selected documents, I place the excerpts beside the current question after the earlier conversation turns to help the model focus on the current material.

9. **I preserved conversation data.** I reused the existing SQLite conversation store. The new mode itself fits in the existing `agent_mode` field. For the additional attachment features, I added `source_files_json` to conversations and `attachments_json` to messages through the database initialization code, with empty defaults that preserve existing history. Reopening a conversation restores sent text, file cards, image previews, and the document selection. I added `PUT /api/conversations/{conversation_id}/sources` to update that selection. Removing a sent document from the selected context keeps its message in history and does not delete the file. I also kept delayed responses attached to their originating conversation and login session.

10. **I fixed local image processing during verification.** The installed Windows Ollama setup initially failed to read a clear test image even through a direct model request. I added `app/deploy/repair_gemma4_vision.py` to create the local alias `gemma4-project-vision:e4b`, using the existing Gemma language-model weights with a separate matching [ggml-org image projector](https://huggingface.co/ggml-org/gemma-4-E4B-it-GGUF/blob/main/mmproj-gemma-4-E4B-it-Q8_0.gguf). This addresses the behavior described in the [upstream Windows vision fix](https://github.com/ollama/ollama/pull/16879). The script verifies the download's SHA-256 and tests image reading before the Windows launcher prefers this alias. The original model remains installed, and an explicitly chosen model takes precedence. I also corrected shutdown of the launcher-owned Ollama process tree so restarts do not leave its model process running.

The user flow I implemented is:

```text
Open Project Assistant
  -> attach a document, code file, or image
  -> optionally write a question
  -> press Send
  -> use the question, or generate an automatic analysis instruction
  -> prepare the relevant document excerpts and image content
  -> ask the local Gemma model
  -> display the sent attachments, optional text, and answer in the chat
```

I retained the existing administrator permission for new uploads and the 30 MB limit per file. A message accepts up to 12 attachments, including up to four images. A conversation can select up to 12 documents. Documents remain in the subject's shared knowledge base, while each conversation keeps its own selection. The upload size limit does not mean that an entire large file fits into the model's context.

I verified the implementation in three ways:

- **Backend checks:** I ran 22 isolated API tests covering the new mode, both subjects and languages, authentication and ownership rules, document retrieval, database migration, message storage, attachment validation, error recovery, and existing Q&A behavior. The tests also cover image-only and file-only messages, empty or whitespace-only instructions, automatic analysis without unrelated earlier material, and image context in follow-up questions. These tests use a model stub to check application behavior independently.
- **Frontend checks:** I checked JavaScript syntax and exercised the interface with a simulated DOM. I verified the example buttons, file picking, drag-and-drop, screenshot pasting, separate drafts, sending text and files together, sending attachments alone, recovery after a failed send, and logout cleanup. Selecting an attachment made no upload request; pressing Send created the request. Automated visual browser review was unavailable during this work.
- **Real-model checks:** I sent an image showing **17**, a Python function that multiplies its input by **3**, and a question asking the model to combine them. The model answered **51** and explained how it used both attachments. I also sent only the image with no TXT file or written question; the model described the number, black font, and white background. Finally, I sent only `SubtractionQuiz.java` with empty text, and the model explained its random numbers, subtraction quiz, input, and control flow. I checked the saved messages and previews, removed the temporary test conversations and files, and preserved the existing Java file.

For my demonstration, I would start the application with `start_installed.bat`, open `http://127.0.0.1:18780`, log in, and select **Project Assistant**. I would first attach `SubtractionQuiz.java`, leave the message box empty, and press **Send** to show automatic code analysis. Next, I would send a screenshot by itself to show image analysis without a TXT file. I would then attach code and a related screenshot together and write: "Explain how this code produces the result shown in the screenshot." This demonstrates automatic analysis, explicit instructions, and the use of text and attachments together.

My implementation is a prompt-based AI Q&A agent with document retrieval, image input, and conversation memory. I reused the existing local model and platform infrastructure. Project Assistant explains material and suggests fixes; editing source files, running shell commands, and automatically inspecting a repository would require a separate execution-tool integration.
